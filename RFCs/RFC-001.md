# RFC-001: Discrete Tracing for AI Compute Fabrics

* **Status:** Draft / Request for Comments
* **Authors:** Prithvi Sai Kavuri (Open Fabric Telemetry contributor)
* **Target:** AI platform and SRE teams; AI runtime, scheduler, accelerator, NIC, and fabric-management maintainers

## 1. Abstract

Modern AI clusters execute work across asynchronous GPU runtimes, RDMA-capable NICs, NVLink or equivalent accelerator fabrics, switches, and schedulers. Much of this work bypasses the host CPU and OS networking stack. Conventional distributed tracing assumes that software creates spans as work runs and propagates trace context with requests. That model is often intrusive, incomplete, or inapplicable in zero-copy accelerator data paths.

This RFC introduces **discrete tracing**: an observability model in which independent systems emit immutable, timestamped execution facts. A collector later reconstructs a topology-aware **fabric execution graph**, diagnostics, and, where justified, optional OpenTelemetry-compatible spans. The workload data path does not construct spans, propagate full trace context, mutate payloads, or synchronize for telemetry.

FabricTrace standardizes the fact model, topology model, join-key rules, data-quality semantics, and deterministic reconstruction requirements needed to apply discrete tracing to AI compute fabrics.

## 2. Motivation

AI platform operators can already collect valuable but disconnected signals:

* schedulers know workload placement and allocation;
* runtimes know batch, graph, kernel, and collective lifecycles;
* accelerators expose activity, health, and counter telemetry;
* NICs and switches expose transport, port, congestion, and error telemetry; and
* fabric-management systems know physical topology.

Existing tools usually expose one layer at a time. A GPU exporter can show utilization or link counters; a runtime profiler can show local GPU activity; application tracing can show a request lifecycle. None provides a portable way to answer a cross-layer operational question such as:

> Why did this distributed job or inference batch become a straggler, and which accelerator, NIC, link, or topology condition was involved?

Classical tracing cannot simply be extended by inserting trace headers into tensors, KV-cache blocks, RDMA payloads, or proprietary fabric packets. Such approaches may be impossible, damage performance, require synchronization, or be unavailable on the relevant hardware.

FabricTrace addresses this gap by standardizing the join of existing evidence, rather than standardizing a new payload or wire-level propagation mechanism.

## 3. Goals

FabricTrace V1 MUST enable an operator to reconstruct an evidence-backed execution graph for an AI workload or serving batch and investigate the following use cases:

1. **Collective stalls:** associate a slow or failed collective with participating ranks, devices, transport endpoints, topology, and observed fabric conditions.
2. **Inference tail latency:** associate a slow prefill or decode batch with placement, accelerator queueing, runtime activity, transport activity, and fabric health.
3. **Placement and noisy-neighbor analysis:** determine whether observed degradation aligns with shared GPUs, NICs, NUMA nodes, PCIe roots, or fabric paths.

V1 MUST permit both passive collection and stronger deterministic correlation where control-plane join keys are available.

## 4. Non-goals

V1 does not:

* standardize NVLink, RDMA, or switch wire metadata;
* require per-packet or per-transfer tracing;
* modify tensors, KV-cache blocks, RDMA payloads, or fabric packets;
* replace OpenTelemetry, Prometheus, DCGM, CUPTI, NCCL/RCCL, eBPF, schedulers, or vendor fabric-management tools;
* capture prompts, model inputs, tensors, KV-cache content, or raw device-memory addresses;
* guarantee automatic root-cause determination; or
* define a canonical user interface or telemetry storage backend.

## 5. Terminology

### 5.1 Discrete tracing

**Discrete tracing** is an observability model in which independent sources emit immutable, timestamped execution facts and collectors reconstruct execution graphs or trace representations after the fact. It does not require span construction or full trace-context propagation in the workload data path.

FabricTrace builds on established event collection, profiling, and post-hoc correlation practices. Its contribution is to formalize these practices for asynchronous AI compute fabrics.

### 5.2 Fabric execution fact

A **fabric execution fact** (or **fact**) is an immutable observation emitted by one source. A fact describes what that source observed; it does not assert a global causal relationship.

### 5.3 Fabric execution graph

A **fabric execution graph** is the collector-produced graph of entities, facts, and relationships reconstructed from a fact set, topology snapshot, clock model, and reconstruction-rule version.

### 5.4 Topology snapshot

A **topology snapshot** is a versioned graph of physical and logical resources and their relationships at a point in time.

### 5.5 Join key

A **join key** is an opaque, scoped identifier emitted by two or more sources that permits deterministic correlation. Examples include scheduler allocation IDs, batch IDs, collective sequence IDs, local runtime operation IDs, queue-pair identifiers, and completion identifiers.

### 5.6 Evidence class

An **evidence class** describes the basis for a graph relationship or output. It is not a general-purpose confidence score.

* `measured`: directly reported by a source.
* `joined`: deterministically linked through a valid shared join key.
* `derived`: deterministically calculated from measured or joined facts.
* `suspected`: a diagnostic hypothesis based on evidence, not an execution-graph edge.

## 6. Design principles

1. **Facts first; spans are derived.** Sources emit facts. Collectors may construct execution graphs, diagnostics, or optional spans after collection.
2. **No workload data-path mutation.** FabricTrace MUST NOT require headers or metadata in application payloads, tensors, KV-cache blocks, RDMA payloads, or fabric packets.
3. **No observability-induced synchronization.** FabricTrace MUST NOT require CPU-GPU synchronization, block a device stream, or delay a collective for telemetry.
4. **Definitive observations; explicit attribution.** Facts MUST retain their origin. Derived output MUST state its evidence class and provenance.
5. **Topology is referenced, not repeated.** Facts SHOULD reference a topology snapshot rather than reproduce topology attributes.
6. **Join keys are control-plane-only and opaque.** A conforming source MAY emit a key at natural workload, batch, collective, or operation boundaries. It MUST NOT require a full trace context in the data plane.
7. **Bounded and loss-aware collection.** Sampling, aggregation, dropped data, capture boundaries, and clock uncertainty MUST be representable.
8. **Vendor-neutral core; pluggable adapters.** The core model describes common concepts. Vendor and runtime integrations translate local telemetry into the model.
9. **Privacy and tenancy safety by default.** Required fields MUST NOT contain application payload data or globally linkable tenant identity.
10. **Interop rather than replacement.** FabricTrace MAY export facts, metrics, graphs, and deterministically derived spans to OpenTelemetry-compatible systems.

## 7. Architecture

```text
Scheduler ──┐
Runtime ───┼── immutable, local Fabric Execution Facts ──┐
GPU ───────┤                                               │
NIC ───────┤                                      collector / reconstructor
Switch ────┤                                               │
Topology ──┘                            fabric execution graph + diagnostics + OTLP
```

Each source independently emits facts within its own capture domain. Node agents or adapters forward facts to a collector. The collector resolves entity identity, selects topology snapshots, accounts for clocks and data quality, joins compatible keys, and reconstructs a graph.

No single source is assumed to observe the full execution path.

## 8. Canonical model

### 8.1 Entities

V1 defines common entity kinds:

* cluster, zone, rack, node;
* workload, job, pod, process;
* accelerator, accelerator partition, NUMA node, PCIe root;
* NIC, switch, port, link, transport endpoint;
* runtime queue or stream, collective communicator, and transport queue pair.

Entity identifiers MUST state their issuer and scope. Adapter-local numeric identifiers MUST NOT be treated as durable cross-node identities without an appropriate stable identity.

### 8.2 Topology snapshots

A topology snapshot MUST have a unique identifier, validity interval, entity inventory, and typed edges. Example edges include `attached_to`, `connected_to`, `hosts`, `uses`, and `routes_through` where the underlying source can support the asserted relationship.

A fact SHOULD carry `topology_snapshot_id`. If the source cannot resolve one, it MUST report that absence rather than guess.

### 8.3 Fact envelope

Every FabricTrace fact MUST include:

```text
fact_id
source_id
source_type
observed_at
clock_domain
clock_uncertainty
event_type
entity_refs
data_quality
```

Facts SHOULD additionally include:

```text
topology_snapshot_id
operation_ref
join_keys
attributes
```

`data_quality` MUST represent at least capture mode, sampling or aggregation details where applicable, and known loss or incompleteness.

### 8.4 V1 event types

The initial event taxonomy includes:

* `workload.allocated`
* `batch.created`
* `batch.dispatched`
* `gpu.operation.submitted`
* `gpu.operation.completed`
* `collective.started`
* `collective.completed`
* `transport.operation.posted`
* `transport.completion.observed`
* `fabric.counter.sampled`
* `fabric.link.state_changed`
* `fabric.error.observed`
* `telemetry.records_dropped`

An adapter MAY emit additional namespaced event types. It MUST document their schema and mapping.

### 8.5 Join-key hierarchy

V1 supports progressively more precise correlation:

```text
job_id → batch_id → operation_id → transport_id
```

A join key MUST document:

* its kind and issuer;
* uniqueness scope and lifetime;
* whether it is reused;
* which source facts can emit it; and
* whether it represents a configured operation, submission, completion, or consumption.

Keys SHOULD reuse identifiers already present at natural control-plane boundaries. If a new key is necessary, implementations SHOULD use a source identity, boot epoch, and monotonic sequence rather than a costly globally generated identifier per transfer.

## 9. Reconstruction and provenance

Given the same fact set, topology snapshot, clock model, and reconstruction-rule version, a conforming collector MUST produce the same fabric execution graph.

The default execution graph MUST contain only `measured`, `joined`, and `derived` relationships. Every derived relationship MUST retain references to the source facts and transformation rule that produced it.

Diagnostic hypotheses MUST be placed in a separate overlay and use `suspected`. A diagnostic output MUST identify its supporting facts, topology snapshot, rule or model version, and known gaps. An implementation MUST NOT display a suspected relationship as a definitive execution edge.

Percent confidence values are OPTIONAL. They MUST NOT be emitted unless their meaning is calibrated and documented. Evidence class and provenance are REQUIRED.

## 10. Operating modes

### 10.1 Passive mode

Passive mode collects existing scheduler, topology, runtime, device, NIC, and switch telemetry without workload instrumentation or data-path modification. It can produce definitive local observations and deterministic derived counter values. Cross-layer attribution is limited when no shared key exists.

### 10.2 Correlated mode

Correlated mode emits small, opaque facts at natural control-plane boundaries such as batch formation, collective submission, or transport posting. It MUST NOT require data-path payload mutation or synchronization. It enables deterministic joins where compatible keys are present.

### 10.3 Forensic mode

Forensic mode is an optional, incident-oriented extension that increases capture fidelity for a bounded interval. It is not required to meet the continuous-collection performance envelope and MUST disclose its sampling and overhead characteristics.

## 11. Performance requirements

FabricTrace does not claim zero total resource cost. Collection, counter reads, buffer writes, and export consume resources.

A V1 implementation MUST be able to demonstrate, for its supported adapters:

* no workload payload mutation;
* no telemetry-induced CPU-GPU synchronization;
* no telemetry-induced device-stream or collective blocking;
* bounded producer memory through non-blocking, bounded buffering or equivalent loss-aware mechanisms; and
* documented collection and export overhead.

The intended property is **zero workload critical-path impact**, not zero resource consumption across the entire system.

## 12. Limitations

* Without a shared join key, passive collection cannot prove per-request or per-transfer causality for overlapping work.
* One-sided RDMA source completion may not prove remote application consumption.
* Counter telemetry can be aggregate, sampled, delayed, unsupported, or shared across tenants.
* GPU, NIC, switch, and host clocks may differ. Facts MUST preserve clock domain and uncertainty; collectors MUST NOT present unsupported ordering as fact.
* A join key can identify a batch or collective without identifying each underlying transfer.
* Topology and routing may change during a workload; a collector MUST preserve the applicable snapshot or report ambiguity.
* Telemetry loss, sampling, and unsupported backend features reduce completeness. They MUST be reported, not hidden.

## 13. Security and privacy

The base schema MUST NOT require prompts, model inputs or outputs, tensors, KV-cache data, raw memory addresses, or other workload payload content.

Join keys SHOULD be opaque and scoped to prevent unintended cross-tenant correlation. Collectors SHOULD enforce tenant-aware access control, retention, and redaction policies. An adapter MUST document any identifiers that can be sensitive in its environment.

## 14. Interoperability

FabricTrace is complementary to OpenTelemetry:

* topology and inventory may map to resources and events;
* counters map to metrics;
* facts map to logs or events;
* a collector MAY export spans only for deterministic, valid relationships.

FabricTrace does not prescribe an OTLP representation for every raw fact in V1. A future RFC will define a normative mapping after the fact and topology schemas stabilize.

## 15. Reference implementation scope

The reference implementation SHOULD target one practical initial environment:

* Kubernetes or Slurm workload allocation adapter;
* CUDA/CUPTI and NCCL runtime adapter;
* DCGM/NVML accelerator and NVLink telemetry adapter;
* InfiniBand/RDMA NIC telemetry adapter, where available;
* topology discovery and snapshot service;
* collector/reconstructor with provenance-preserving graph output; and
* OTLP exporter plus example dashboards and recorded incident datasets.

The reference implementation is not the standard. Its purpose is to validate the schema, conformance requirements, and critical-path performance claims.

## 16. Success criteria

V1 is successful when a reproducible cluster experiment shows that an operator can investigate a collective slowdown or inference tail-latency regression faster, and with clearer evidence, than by manually combining application traces, runtime logs, GPU metrics, and fabric dashboards.

The project SHOULD publish:

* a versioned schema and compatibility policy;
* topology and event conformance fixtures;
* recorded multi-node incident datasets;
* deterministic reconstruction tests;
* adapter conformance tests;
* data-loss and clock-uncertainty tests; and
* performance results demonstrating the requirements in Section 11.

## 17. Open questions

1. What common identifier and privacy model best supports multi-tenant scheduler correlation?
2. Which runtime and transport lifecycle boundaries provide the best V1 join keys without affecting workload critical paths?
3. How should collectors model dynamic routing and multipath fabrics when a physical path is not directly observable?
4. Which fact serialization and transport formats should be normative, if any, after V1 schema validation?
5. Which cross-vendor adapters are sufficient to validate that the core model is genuinely vendor-neutral?
